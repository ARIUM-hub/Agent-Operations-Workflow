# 问题簇处理任务闭环设计

## 背景

客户使用问题归因智能体已经具备会话导入、确定性分析、人工复核、筛选导出、运营概览、高频问题簇、趋势对比和异常提示能力。运营可以发现问题集中方向和近期明显上升项，但发现问题后仍需要在工作台之外记录处理动作，无法持续追踪责任团队、优先级、截止时间和最终结论。

本轮目标是在不接入数据库、不调用模型供应商、不增加后台轮询或外部通知的前提下，把高频问题簇和趋势问题簇转为本地处理任务，形成“发现问题、创建任务、开始处理、记录结果、完成复盘”的运营闭环。

## 目标

1. 支持从高频问题簇和趋势问题簇人工创建处理任务。
2. 每个任务按“平台 + 问题类型 + 责任方”标识问题簇，并保存创建时匹配记录的快照。
3. 自动建议责任团队、优先级和截止日期，允许运营在创建或处理过程中修改。
4. 支持“待处理 → 处理中 → 已完成”的单向状态流程。
5. 完成任务时必须填写处理结果，保留可复盘结论。
6. 同一问题簇同时只允许一个未完成任务，完成后允许创建新一轮任务。
7. 在工作台中统一查看、筛选和下钻处理任务。
8. 任务接口或任务区域失败时，不影响分析、复核、趋势、筛选和导出。

## 非目标

- 不按单条客户记录创建任务。
- 不自动创建任务，只提供人工创建入口。
- 不分配具体人员姓名，只管理责任团队。
- 不支持自定义任务状态或状态回退。
- 不支持删除、归档、重新打开已完成任务。
- 不发送邮件、短信、站内通知或外部平台消息。
- 不接入 Amazon、TikTok Shop 或其他海外电商平台 API。
- 不增加数据库、消息队列、定时器、后台任务或第三方前端依赖。
- 不调用模型，不增加供应商、代理通道或本地转发请求。
- 不修改分析记录、反馈事件或现有 CSV 字段。

## 方案比较

### 采用：独立任务 JSONL 事件流

新增 `data/tasks.jsonl`，任务创建和更新都以追加事件写入。读取时按任务 ID 重建每个任务的最新状态，已完成任务保留历史，后续相同问题簇可以创建新一轮任务。

优点：

- 与分析和反馈存储解耦，不改变已有 `analyses.jsonl` 语义。
- 所有任务变更都有时间戳和追加记录，便于复盘。
- 保持现有本地文件架构，不引入数据库或迁移工具。
- 后续增加任务导出或任务历史查看时边界清晰。

代价是本地多一个 JSONL 文件，并需要独立的事件重建逻辑。

### 不采用：写入现有分析 JSONL

把任务事件与分析、反馈事件放在同一个文件可以减少文件数量，但会让 `AnalysisStore` 同时理解三类业务对象。任务生命周期与分析记录生命周期不同，混合后会增加读取、迁移、测试和故障隔离成本。

### 不采用：浏览器本地存储

浏览器 `localStorage` 实现较快，但更换浏览器、清理缓存或更换用户配置会丢失任务，也无法被后端接口、测试和后续导出可靠复用，不适合作为运营任务记录。

## 架构与模块边界

新增两个聚焦模块：

```text
src/customer_issue_agent/task_storage.py
src/customer_issue_agent/tasks.py
```

- `task_storage.py` 只负责追加任务事件和重建任务最新状态，不实现业务默认值或状态规则。
- `tasks.py` 负责字段校验、问题簇匹配、任务默认值、截止日期、状态转换和未完成任务去重。
- `app.py` 只负责解析 HTTP 参数、调用任务服务并映射错误状态码。
- `app.js` 负责任务区域加载、表单交互、筛选、状态更新和记录下钻。
- `AnalysisStore`、趋势模块、概览模块和反馈语义保持不变。

`create_app(storage_path=None, task_storage_path=None)` 默认把任务文件放在分析文件同目录下，文件名为 `tasks.jsonl`。测试通过 `task_storage_path` 注入独立任务路径，避免共享状态。

## 任务数据模型

任务最新状态使用以下字段：

```json
{
  "id": "task-uuid",
  "title": "Amazon · 功能不会用或设置失败 · 客服培训",
  "created_at": "2026-08-03T08:00:00+00:00",
  "updated_at": "2026-08-03T08:00:00+00:00",
  "source": "trend",
  "source_range": "7d",
  "platform": "Amazon",
  "issue_category": "function_use",
  "responsibility": "customer_service_training",
  "record_ids": ["record-1", "record-2", "record-3"],
  "record_count": 3,
  "significant_increase": true,
  "team": "customer_service_training",
  "priority": "high",
  "due_date": "2026-08-06",
  "status": "pending",
  "result": null,
  "completed_at": null
}
```

枚举范围：

- `source`：`summary`、`trend`。
- `source_range`：`all`、`7d`、`30d`；趋势来源固定为 `7d`。
- `team`：复用现有责任方枚举，即运营、客服培训、产品、供应链或质量、需要补充信息。
- `priority`：`low`、`medium`、`high`。
- `status`：`pending`、`in_progress`、`completed`。

任务标题由问题簇中文标签确定性生成，不支持自由编辑。`record_count` 必须等于 `record_ids` 长度。任务记录保存原始分析字段，不使用人工修正字段改写问题簇口径，与现有概览和趋势保持一致。

## 任务事件模型

创建事件保存任务完整初始状态：

```json
{
  "type": "task_created",
  "task": {
    "id": "task-uuid",
    "title": "Amazon · 功能不会用或设置失败 · 客服培训",
    "created_at": "2026-08-03T08:00:00+00:00",
    "updated_at": "2026-08-03T08:00:00+00:00",
    "source": "trend",
    "source_range": "7d",
    "platform": "Amazon",
    "issue_category": "function_use",
    "responsibility": "customer_service_training",
    "record_ids": ["record-1", "record-2", "record-3"],
    "record_count": 3,
    "significant_increase": true,
    "team": "customer_service_training",
    "priority": "high",
    "due_date": "2026-08-06",
    "status": "pending",
    "result": null,
    "completed_at": null
  }
}
```

更新事件只保存任务 ID、更新时间和已校验变更：

```json
{
  "type": "task_updated",
  "task_id": "task-uuid",
  "updated_at": "2026-08-04T08:00:00+00:00",
  "changes": {
    "status": "in_progress"
  }
}
```

`TaskStore.list_tasks()` 按文件顺序应用事件。不存在的文件返回空列表；空行跳过。未知事件类型、缺少任务 ID 或引用不存在任务的更新事件视为损坏数据，抛出明确存储错误，不静默伪造任务状态。任务区域捕获该错误并独立降级。

所有文本使用 UTF-8，JSON 序列化使用 `ensure_ascii=False`，每个事件固定占一行并以 `\n` 结尾。

## 问题簇身份与去重

任务去重键为：

```text
platform + issue_category + responsibility
```

- 三个字段先去除首尾空白；平台使用不区分大小写的精确比较。
- 问题类型和责任方必须属于现有枚举。
- `unknown` 平台、非法问题类型或非法责任方不能创建任务。
- 来源和统计范围不参与去重。同一问题簇无论从高频问题或趋势问题进入，都复用当前未完成任务。
- 状态为 `pending` 或 `in_progress` 的任务视为未完成任务。
- 创建时找到未完成任务，返回该任务并设置 `created: false`，不追加事件。
- 同一问题簇的旧任务全部完成后，可以创建新任务，形成独立处理轮次。

## 记录快照

客户端只提交问题簇、来源和统计范围，不提交可信记录 ID。后端重新读取 `AnalysisStore.list_records()` 并按以下规则匹配：

- 平台不区分大小写精确匹配，不使用关键词包含匹配。
- 问题类型和责任方精确匹配原始分析字段。
- 高频问题来源使用创建时页面选择的 `all`、`7d` 或 `30d`。
- 趋势来源忽略客户端范围并固定使用最近 `7d`。
- 有效时间范围排除缺失、非法和未来 `created_at`。
- 匹配结果按分析文件顺序保存记录 ID 快照。
- 没有匹配记录时返回 `422`，不创建空任务。

快照创建后保持不变。后续新增分析、保存反馈或时间推进都不修改既有任务的 `record_ids` 和 `record_count`。

## 默认责任团队、优先级和截止日期

责任团队默认等于问题簇责任方，创建表单允许修改为其他合法责任团队。

优先级建议：

- 趋势来源且后端重新计算确认 `significant_increase == true`：默认 `high`。
- 其他高频或普通趋势问题簇：默认 `medium`。
- 运营可以在创建表单中改为 `low`、`medium` 或 `high`。

截止日期按创建当天的本机日历日期计算：

- `high`：加 3 天。
- `medium`：加 7 天。
- `low`：加 14 天。

客户端显示后端返回的建议日期。创建时运营可以修改日期。任务创建后调整优先级不会静默覆盖已有截止日期；只有更新请求显式包含 `due_date` 时才修改日期。

## 状态转换与完成规则

状态只允许单向转换：

```text
pending -> in_progress -> completed
```

- `pending` 任务可以修改责任团队、优先级和截止日期，或进入 `in_progress`。
- `in_progress` 任务可以修改责任团队、优先级和截止日期，或填写处理结果后进入 `completed`。
- `pending` 不能直接跳到 `completed`。
- `completed` 任务不可重新打开或继续编辑；需要处理同一问题簇时创建新一轮任务。
- 进入 `completed` 时 `result` 去除首尾空白后必须非空，并写入 `completed_at` UTC 时间。
- 非完成状态的 `result` 固定为 `null`。

非法状态转换返回 `409`；字段校验失败或完成结果为空返回 `422`；任务不存在返回 `404`。

## API 设计

### 获取任务

```text
GET /api/tasks?status=&priority=
```

支持合法状态和优先级精确筛选。未知筛选值返回 `422`。响应中的 `counts` 始终统计全部任务，`tasks` 才应用筛选：

```json
{
  "counts": {
    "pending": 2,
    "in_progress": 1,
    "completed": 4
  },
  "tasks": []
}
```

默认排序为：未完成任务在前，逾期任务优先，其次按优先级高到低、截止日期升序、创建时间降序；已完成任务按完成时间降序。

### 创建任务

```text
POST /api/tasks
```

表单字段：

- `source`
- `source_range`
- `platform`
- `issue_category`
- `responsibility`
- `team`
- `priority`
- `due_date`

后端重新计算记录快照和趋势异常标记。响应：

```json
{
  "created": true,
  "task": {}
}
```

新建成功返回 `201`；复用已有未完成任务返回 `200` 和 `created: false`。

### 更新任务

```text
PATCH /api/tasks/{task_id}
```

使用 JSON 请求体，允许字段：

- `team`
- `priority`
- `due_date`
- `status`
- `result`

未知字段返回 `422`，空更新返回 `422`。响应返回更新后的完整任务。

## 页面区域

在趋势区下方、最近记录上方新增：

```text
处理任务
```

顶部展示待处理、处理中、已完成三个数量指标，并提供状态、优先级筛选。任务使用响应式卡片而不是宽表格，保证桌面和移动端可读。

每张任务卡展示：

- 自动标题。
- 高频问题或趋势来源标签。
- 关联记录数量。
- 责任团队。
- 优先级。
- 截止日期。
- 状态。
- 已完成任务的处理结果和完成时间。

未完成且截止日期早于本机当天的任务显示“已逾期”。方向、优先级和逾期不能只依赖颜色表达，必须同时有中文文字标签。

## 创建任务交互

高频问题和趋势问题簇都提供独立“创建任务”按钮。原问题簇标题继续作为筛选下钻按钮，两个交互必须是兄弟元素，不能产生嵌套按钮。

点击“创建任务”后打开轻量创建表单：

1. 显示问题簇中文标题、来源和统计范围。
2. 前端按责任方、明显上升标记和固定 3/7/14 天规则显示初始建议；后端在提交时重新计算记录快照和明显上升标记，并再次校验所有字段。
3. 允许运营修改责任团队、优先级和截止日期。
4. 提交期间禁用按钮，防止重复点击。
5. 新建成功后关闭表单并刷新任务区域一次。
6. 返回 `created: false` 时关闭表单、刷新任务区域、滚动并高亮已有任务，不显示为错误。

明显上升的默认高优先级必须由后端重新计算确认，不能只信任客户端数据属性。

## 任务处理交互

- 待处理任务显示“开始处理”和“编辑”。
- 处理中任务显示“完成任务”和“编辑”。
- 点击“编辑”展开责任团队、优先级和截止日期表单。
- 点击“完成任务”展开处理结果文本框；空结果在前端提示并由后端再次校验。
- 已完成任务只读，不显示编辑或重新打开操作。
- 更新成功后只刷新任务区域一次。
- 更新失败保留当前表单和值，显示局部错误，不改变页面中的既有任务状态。

## 任务记录下钻

点击任务的关联记录数量后：

1. 把概览范围切换为任务保存的 `source_range`。
2. 设置平台精确匹配、问题类型和责任方筛选。
3. 保留已有关键词和复核状态。
4. 刷新最近记录本地筛选、筛选导出条件和预计数量。
5. 重新加载对应范围的运营概览。
6. 滚动到最近记录区域。

页面最近记录仍只显示当前 10 条样本；预计数量和筛选 CSV 基于全部本地 JSONL。任务保存的记录 ID 快照用于任务依据和数量，不把最近记录列表改造成完整历史记录查看器。

## 刷新策略

- 页面 `DOMContentLoaded`：加载任务区域一次。
- 创建任务成功：刷新任务区域一次。
- 更新任务成功：刷新任务区域一次。
- 状态或优先级筛选变化：按筛选条件重新加载任务。
- 单条或批量分析成功：不刷新任务，既有任务快照不变且不自动建任务。
- 反馈保存：不刷新任务。
- 概览范围、普通记录筛选和趋势加载：不刷新任务。
- 不增加定时器、自动轮询、失败重试循环或后台任务。

任务列表 GET 请求沿用趋势和导出预计数量的最新请求序号模式，较旧列表响应不得覆盖较新的筛选或更新结果。创建和更新请求在对应表单提交期间禁用按钮，每个表单同一时间只允许一个写请求。

## 错误与边界处理

- 任务文件不存在：返回全零数量和空列表。
- 任务文件损坏：任务区域显示“任务数据读取失败”，其他区域继续可用。
- 无效或 `unknown` 问题簇：不渲染创建按钮；后端收到请求仍返回 `422`。
- 创建时没有匹配记录：返回 `422`，表单保留并显示原因。
- 同一问题簇已有未完成任务：返回已有任务，不追加重复事件。
- 更新不存在任务：返回 `404`。
- 非法状态转换：返回 `409`。
- 完成结果为空：返回 `422`。
- 创建或更新请求失败：不提前修改本地任务卡。
- 较旧列表请求后返回：忽略该响应，不覆盖最新列表。
- 页面缺少任务容器：加载函数直接返回，不发请求。

## 测试策略

### 存储测试

- 文件不存在返回空列表。
- 创建事件和更新事件按顺序重建最新任务。
- 多任务和同一问题簇多轮历史保持独立。
- UTF-8 中文处理结果原样保存。
- 未知、缺失和悬空更新事件产生明确存储错误。

### 任务服务测试

- 高频问题使用 `all`、`7d` 或 `30d` 快照范围。
- 趋势问题固定使用 `7d`，排除未来和非法时间。
- 平台、问题类型和责任方精确匹配。
- 空匹配和无效问题簇被拒绝。
- 明显上升默认高优先级，其他默认中优先级。
- 三种优先级生成 3、7、14 天建议截止日期。
- 合法自定义责任团队、优先级和截止日期生效。
- 同一问题簇未完成任务去重。
- 完成后允许创建新一轮任务。
- 状态只能按顺序前进。
- 完成结果必填，已完成任务不可编辑。

### API 与模板契约测试

- 三个任务接口返回规定状态码和响应结构。
- 状态、优先级、日期和更新字段校验完整。
- 首页包含任务区域、数量指标、筛选和可访问标签。
- 高频与趋势问题簇包含独立创建入口。
- JavaScript 和 CSS 包含任务加载、表单、卡片、状态、逾期和移动端钩子。

### 前端行为测试

使用 Node 内置 `node:test`、`assert`、`vm` 和轻量 DOM stub 加载真实 `app.js`，覆盖：

- 任务卡按状态显示正确操作。
- 状态和优先级筛选生成正确请求。
- 高频问题使用当前概览范围创建。
- 趋势问题固定使用 `7d` 创建。
- 创建成功刷新一次任务区域。
- 重复任务滚动并高亮已有卡片。
- 编辑成功和开始处理各刷新一次。
- 空处理结果不提交，合法结果完成任务。
- 更新失败保留表单和既有任务状态。
- 任务记录下钻设置精确问题簇和保存范围，并保留关键词和复核状态。
- 较旧任务响应不覆盖最新结果。

## 验收标准

1. 高频问题和趋势问题簇均可人工创建处理任务。
2. 任务保存创建时精确匹配的记录 ID 快照和数量。
3. 明显上升问题默认高优先级，其他问题默认中优先级。
4. 截止日期按优先级建议为 3、7 或 14 天，并允许修改。
5. 同一问题簇不会同时出现多个未完成任务。
6. 任务只能从待处理进入处理中，再填写处理结果完成。
7. 已完成任务保持只读，同一问题簇可创建新一轮任务。
8. 工作台显示任务数量、筛选、责任团队、优先级、截止日期、状态、逾期和处理结果。
9. 点击任务关联记录可以恢复任务范围和精确问题簇筛选，并保留关键词与复核状态。
10. 创建、重复定位、编辑、开始处理和完成失败均有局部中文反馈。
11. 任务接口失败不影响分析、复核、趋势、筛选和导出。
12. 不新增数据库、自动建任务、外部通知、后台轮询或模型调用。
13. pytest、Node 行为测试、JavaScript 语法、UTF-8 和差异检查全部通过。

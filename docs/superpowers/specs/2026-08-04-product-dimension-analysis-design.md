# 商品维度分析设计

## 背景

客户使用问题归因智能体已经支持多海外电商平台会话分析、批量上传、人工复核、筛选导出、运营概览、问题趋势、问题簇任务和任务效果复盘。当前分析记录只保存平台和会话内容，运营只能按平台、问题类型和责任方定位问题，无法回答以下问题：

- 哪些内部 SKU 的客户使用问题最多？
- 同一 SKU 在 Amazon、TikTok Shop、Shopee 等平台是否同时出现问题？
- 某个 SKU 的问题是否在近 7 天明显上升？
- 从 SKU 问题簇创建任务后，效果复盘是否只比较该 SKU 的记录？

本轮目标是在不接入平台 API、不调用模型供应商、不增加后台轮询的前提下，为分析记录增加店铺、内部 SKU 和平台商品 ID，并把 SKU 维度贯通到筛选、导出、概览、趋势、任务和效果复盘。

## 目标

1. 单条粘贴、普通文件上传和批量文件上传都可以携带商品信息。
2. 每条分析记录可选保存店铺、内部 SKU 和平台商品 ID。
3. 最近记录、筛选导出和导出数量预览支持三个商品字段。
4. 运营概览展示 SKU 覆盖情况、Top SKU 和 SKU 高频问题簇。
5. 近 7 天趋势展示 SKU 问题簇变化。
6. SKU 问题簇可以创建 SKU 范围任务。
7. SKU 任务的记录快照、显著上升判断和效果复盘都严格限制在对应 SKU。
8. 历史无商品字段记录继续正常读取和参与原有分析。

## 非目标

- 不从客服会话文本自动猜测 SKU、ASIN、店铺或商品 ID。
- 不接入 Amazon、TikTok Shop 或其他海外电商平台 API。
- 不建立 SKU 与 ASIN、Product ID 之间的主数据映射表。
- 不允许人工反馈修改商品元数据。
- 店铺和平台商品 ID 暂不进入任务去重键。
- 不新增数据库、消息通知、后台队列或自动轮询。
- 不新增模型调用、供应商探测、批量重试或压力测试。
- 不重写或批量迁移历史 `analyses.jsonl` 和 `tasks.jsonl`。

## 方案选择

### 采用：扩展现有分析记录链路

在 `AnalysisRequest` 中直接增加三个可选字段，继续由 `AnalysisResult` 写入现有 `analyses.jsonl`。现有筛选、汇总、趋势和任务模块从同一记录读取商品信息。

选择理由：

- 商品信息与原始分析请求属于同一事实，放在同一记录中最容易理解。
- 所有下游功能共享一个数据口径，不需要跨 JSONL 文件合并。
- Pydantic 默认值可以自然兼容历史记录。
- 当前单机、单 worker、低并发架构不需要新增数据库。

### 不采用：独立商品元数据 JSONL

按记录 ID 另存商品信息虽然不改变原分析结构，但每次筛选、导出、趋势和任务计算都需要跨文件投影，并引入丢失事件、重复事件和文件损坏的一致性问题。

### 不采用：独立商品分析页面与 API

独立模块会重复现有筛选、时间范围、趋势、任务和错误降级逻辑，运营也需要在两个页面之间切换，不符合本轮端到端贯通的目标。

## 数据模型

### 分析请求

`AnalysisRequest` 新增三个字段：

```python
store_name: str = ""
sku: str = ""
platform_product_id: str = ""
```

三个字段都遵循以下规则：

- 可为空。
- 非空时必须是字符串。
- 去除首尾空格后保存。
- 最长 200 个字符。
- 保留原始大小写和内部字符，不自动转大写、不改写连字符。
- 不把 `Unknown` 视为特殊空值；只有真正空字符串代表未填写。

`AnalysisResult` 继续内嵌完整 `AnalysisRequest`，因此存储结构不需要额外顶层字段。

### 兼容历史记录

读取记录时必须使用空字符串作为缺失商品字段的逻辑默认值。历史 JSONL 不做迁移，不追加补丁事件，不因缺少商品字段报错。

原有平台、问题类型、责任方、反馈和任务仍按当前规则工作。无 SKU 记录继续参与原有总量、平台分布、高频问题和普通趋势，但不进入 SKU 排名、SKU 问题簇或 SKU 趋势。

### 商品标识规范值

展示和 CSV 导出使用记录中保存的原始文本。筛选、聚合和任务去重使用：

```text
trimmed_value.casefold()
```

规范值只用于比较，不写回记录。这样 `sku-01` 与 `SKU-01` 归为同一 SKU，同时保留首次记录的原始显示文本。

同一规范 SKU 存在不同显示形式时，聚合结果使用时间范围内按文件顺序首次出现的非空形式，排序仍使用规范值保证确定性。

## 输入流程

### 页面表单

粘贴会话、普通文件上传和批量上传表单都增加三个可选输入：

- 店铺
- SKU
- 平台商品 ID

字段放在平台输入之后，三个表单使用独立 ID，但提交参数名统一为 `store_name`、`sku`、`platform_product_id`。商品字段为空时不影响原有分析。

### TXT 和 LOG

- 单条文件：使用表单中的商品默认值。
- 批量分段文件：每个分段都使用同一组表单默认值。
- 不从文本正文解析商品字段。

### CSV 和 Excel 列别名

表头匹配不区分大小写并去除首尾空格。每个字段使用固定别名优先级：

```text
店铺：store_name, store, shop_name, shop, 店铺名称, 店铺
SKU：sku, seller_sku, merchant_sku, product_sku, 商品sku, 商品 SKU
平台商品 ID：platform_product_id, product_id, asin, item_id, listing_id, 商品id, 商品 ID
```

同一行出现多个别名列时，只取优先级最高的第一个非空值，不依赖实际列顺序。

### 普通表格文件

`/api/analyze-file` 把整个文件视为一条会话。商品列可以在多行重复：

- 同一字段所有非空单元格规范后相同：使用第一条原始文本。
- 同一字段出现多个不同规范值：返回 `422`，提示单条文件包含多个商品标识，要求改用批量上传或整理文件。
- 文件商品值优先于表单默认值；文件无值时使用表单值。

这可以避免把包含多个 SKU 的消息明细错误保存为单条商品分析。

### 批量表格文件

现有批量解析结果从 `list[str]` 升级为结构化输入列表，每项包含：

```python
conversation_text: str
store_name: str
sku: str
platform_product_id: str
```

每行商品字段优先于表单默认值，行内为空时回退到表单值。会话文本列继续使用现有别名规则。

在进入分析和写入循环之前，系统必须完成整批会话数量、会话文本和商品字段校验。任一行商品字段非法时整个请求返回 `422`，不写入部分分析记录。

### Excel 数值单元格

数字型商品 ID 转为稳定文本：

- 整数不附加 `.0`。
- 非整数使用非科学计数法的十进制文本。
- 布尔值和日期不作为合法商品标识，返回 `422`。
- 需要保留前导零的 SKU 或商品 ID 必须在源表中设置为文本；数值单元格已经丢失的前导零无法恢复。

## 分析与存储流程

`_run_analysis()` 改为接收完整 `AnalysisRequest` 所需字段，统一完成 Pydantic 校验，再执行解析、归因、报告和存储。会话解析和归因规则不读取商品信息，避免商品标识影响问题类型判断。

数据流为：

```text
表单默认值 + 文件行级值
  -> 输入提取与固定优先级合并
  -> 整批商品字段预校验
  -> AnalysisRequest
  -> 现有会话解析与归因
  -> AnalysisResult
  -> analyses.jsonl
```

存储仍使用 UTF-8、`ensure_ascii=False` 和 LF 换行，不创建新的数据文件。

## 筛选、搜索与导出

### 后端筛选参数

`filter_records()`、CSV 导出和导出数量端点新增：

```text
store_name
sku
platform_product_id
```

匹配规则：

- `store_name`：去除首尾空格后，不区分大小写的包含匹配。
- `sku`：去除首尾空格后，不区分大小写的精确匹配。
- `platform_product_id`：去除首尾空格后，不区分大小写的精确匹配。

商品字段必须与平台、问题类型、责任方、复核状态、关键词和时间范围组合使用，CSV 导出与数量预览必须复用同一个 `filter_records()` 口径。

### 前端筛选

最近记录筛选区增加店铺、SKU 和平台商品 ID 输入框。商品洞察下钻写入精确值；人工输入 SKU 和平台商品 ID也按精确值处理。清空按钮同时清空三个新字段。

筛选条件摘要明确显示商品条件，例如：

```text
平台：Amazon；店铺：US Store；SKU：SKU-01；最近 7 天
```

关键词搜索文本加入店铺、SKU 和平台商品 ID，使用户可以通过现有关键词框找到商品记录，但关键词搜索不替代结构化精确筛选。

### CSV 字段

现有 CSV 在平台列之后增加：

- 店铺
- SKU
- 平台商品 ID

继续使用 UTF-8 with BOM。历史空值导出为空单元格，不输出 `unknown`。

## 运营概览

现有 `/api/records/summary?range=` 响应增加：

```json
{
  "product_coverage": {
    "with_sku": 0,
    "missing_sku": 0
  },
  "top_skus": [],
  "top_sku_issue_clusters": []
}
```

### SKU 覆盖情况

- `with_sku`：当前 summary 时间范围内 SKU 非空的记录数。
- `missing_sku`：当前范围内 SKU 为空或缺失的记录数。
- 两者之和必须等于 `total_records`。

### Top SKU

按 SKU 规范值跨平台汇总，返回全部有 SKU 项，由前端展示前五项。每项包含：

```json
{
  "sku": "SKU-01",
  "count": 12,
  "platform_count": 2,
  "platforms": ["Amazon", "TikTok Shop"]
}
```

排序规则：记录数降序、SKU 规范值升序、显示文本升序。`platforms` 使用去重后的确定性排序。

### SKU 高频问题簇

按以下键聚合：

```text
platform + sku_normalized + issue_category + responsibility
```

每项包含平台、SKU 原始显示文本、问题类型、责任方和数量。只返回前五项，排序沿用现有高频问题簇的数量优先和确定性字典序。

无 SKU 记录不进入 `top_skus` 和 `top_sku_issue_clusters`，但通过 `missing_sku` 明确展示覆盖缺口。

## SKU 近 7 天趋势

现有 `/api/records/trends?period=7d` 响应保留普通 `clusters`，新增 `sku_clusters`。

SKU 趋势键为：

```text
platform + sku_normalized + issue_category + responsibility
```

周期边界、非法或未来时间排除、变化计算和异常阈值完全复用普通趋势：

- 当前周期：`[now - 7d, now]`
- 上一周期：`[now - 14d, now - 7d)`
- `delta = current_count - previous_count`
- 当前至少 3 条且增量至少 2 条时 `significant_increase=true`
- 变化为零的项不返回

`sku_clusters` 按绝对变化、当前数量、平台、SKU、问题类型和责任方确定性排序。前端展示前五项。

无 SKU 记录不进入 SKU 趋势，但仍进入普通趋势。趋势只在现有页面初始化、单条分析成功和批量分析完成后刷新，不新增自动轮询。

## 前端商品洞察

运营概览中的商品区域包含：

1. SKU 覆盖卡：显示有 SKU 与未填写 SKU 数量。
2. Top SKU 列表：显示 SKU、记录数和涉及平台数。
3. SKU 高频问题列表：显示平台、SKU、问题类型、责任方和数量。

趋势区域增加 SKU 趋势列表，视觉层级与普通趋势一致，但明确标记 SKU。

交互规则：

- 点击 Top SKU：设置 SKU 精确筛选，不强制改变平台。
- 点击 SKU 高频问题或 SKU 趋势：设置平台、SKU、问题类型和责任方精确筛选。
- 下钻保留关键词和人工复核状态。
- SKU 趋势下钻把 summary 和导出范围切换到最近 7 天。
- 无效、空或 `unknown` SKU 项只读，不触发下钻和任务创建。

前端继续使用请求序号保护，较旧 summary、trend 或导出数量响应不能覆盖较新的筛选和分析结果。

## SKU 范围任务

### 创建载荷

任务创建表单和 `POST /api/tasks` 增加可选 `sku`。从普通问题簇创建时为空；从 SKU 高频问题或 SKU 趋势创建时必填。

SKU 任务保存字段：

```json
{
  "sku": "SKU-01"
}
```

历史任务缺少 `sku` 时按空字符串处理。

### 去重键

无 SKU 任务保持原键：

```text
platform + issue_category + responsibility
```

SKU 任务使用：

```text
platform + sku_normalized + issue_category + responsibility
```

SKU 任务与同问题簇的无 SKU 任务可以同时存在，因为两者处理范围不同。SKU 任务之间使用不区分大小写的 SKU 规范值去重。

### 记录快照

SKU 任务创建时重新读取 `analyses.jsonl`，按以下条件匹配：

- 平台精确、不区分大小写。
- SKU 精确、不区分大小写。
- 问题类型精确。
- 责任方精确。
- 时间范围沿用任务来源规则。
- 排除缺失、非法、未来或范围外时间。

无匹配记录时返回 `422`，不创建空任务。

### 显著上升与优先级

SKU 趋势任务的 `significant_increase` 必须按 SKU 范围重新计算，不直接信任前端标记。达到原有阈值时默认高优先级，否则默认中优先级。

### 任务展示与下钻

- SKU 任务标题包含平台、SKU、问题类型和责任方。
- 任务卡显示 SKU 标签。
- 点击关联记录时恢复平台、SKU、问题类型、责任方和保存的时间范围。
- 无 SKU 任务卡与交互保持现状。

## SKU 任务效果复盘

SKU 任务的创建前 7 天和完成后 7 天窗口都必须附加 SKU 精确匹配。普通无 SKU 任务保持现有平台、问题类型和责任方口径。

SKU 匹配必须统一用于：

- 创建任务时的记录 ID 快照。
- 趋势来源任务的显著上升重算。
- 创建前 7 天证据。
- 完成后 7 天证据。

这样可以防止同平台其他 SKU 的记录污染效果结论。复盘事件结构不重复写入 SKU，读取任务创建事件中的 SKU 即可。

## 错误处理与降级

- 表单商品字段不合法：FastAPI/Pydantic 返回 `422`，不保存分析。
- 批量任一行商品字段不合法：整批返回 `422`，商品预校验阶段不写入记录。
- 单条表格出现冲突商品值：返回 `422`，提示拆分文件或使用批量上传。
- 文件类型、编码、空内容和 50 条限制继续沿用现有错误。
- 损坏 `analyses.jsonl`：沿用 `AnalysisStorageError`，依赖分析数据的 API 返回现有错误；静态页面和不依赖该文件的能力保持可用。
- 损坏 `tasks.jsonl`：沿用任务存储错误映射，不影响分析、筛选、概览和导出。
- 商品概览或趋势前端渲染失败：只在对应区域显示错误，不清空最近记录和任务。
- 不增加自动重试、后台恢复或外部请求。

## 主要代码边界

预计修改：

- `domain.py`：商品字段模型与校验。
- `ingestion.py`：结构化批量输入、别名提取、表格冲突检测和数值转换。
- `app.py`：三个分析端点、筛选端点和任务端点参数传递。
- `record_filters.py`：店铺包含匹配、SKU 与平台商品 ID 精确匹配。
- `export.py`：三个 CSV 字段。
- `summary.py`：覆盖率、Top SKU、SKU 高频问题。
- `trends.py`：SKU 趋势。
- `tasks.py`：可选 SKU 去重、快照、显著上升和复盘匹配。
- `templates/index.html`：输入、筛选和任务隐藏字段。
- `static/app.js`：商品洞察、筛选、下钻、任务创建和旧响应保护。
- `static/styles.css`：桌面与移动布局。
- `README.md`：商品字段输入、列别名、筛选、洞察和 SKU 任务说明。

不新增生产依赖，不修改服务启动脚本和计划任务。

## 测试策略

### 领域与输入

- 商品字段为空、去空格、长度边界和非字符串拒绝。
- TXT/LOG 使用表单默认值。
- CSV/XLSX 固定别名优先级和大小写不敏感表头。
- 普通表格重复一致值、冲突值和默认值回退。
- 批量行级值覆盖、空值回退、整批预校验和 50 条限制。
- Excel 整数、非整数、布尔值、日期和前导零说明。

### 存储与兼容

- 新分析保存三个商品字段。
- 历史无字段记录正常读取。
- UTF-8 中文店铺和 SKU 不使用 `\uXXXX` 转义。
- 人工反馈事件不改变商品字段。

### 筛选与导出

- 店铺包含匹配。
- SKU 和平台商品 ID 精确、不区分大小写匹配。
- 商品条件与现有筛选组合。
- CSV 字段顺序、BOM、中文和历史空值。
- 导出数量与真实导出条数一致。

### 概览与趋势

- SKU 覆盖数之和等于总数。
- Top SKU 跨平台聚合、显示文本选择和确定性排序。
- SKU 高频问题 Top 5。
- SKU 趋势周期边界、阈值、并集、未来与非法时间排除。
- 无 SKU 记录只参与普通概览和普通趋势。

### 任务与复盘

- SKU 与无 SKU 任务去重键相互独立。
- SKU 大小写差异仍去重。
- SKU 快照只包含正确商品记录。
- SKU 趋势优先级按后端重算。
- SKU 复盘两个窗口不混入其他 SKU。
- 历史任务无 SKU 时保持原有行为。

### 前端

- 三种表单提交商品字段。
- 商品筛选、摘要和导出 URL 参数一致。
- Top SKU、SKU 高频问题和 SKU 趋势渲染。
- 下钻保留关键词与复核状态并应用精确 SKU。
- SKU 任务草稿、任务卡和记录下钻。
- 较旧响应不能覆盖新筛选或新洞察。
- 现有分析、反馈、普通趋势和任务测试不回归。
- 真实浏览器桌面和 390×844 移动视口验收。

## 验收标准

1. 单条和批量分析都能保存店铺、SKU 和平台商品 ID。
2. 表格行级商品字段按固定别名优先级覆盖表单默认值。
3. 历史无商品字段记录无需迁移即可正常使用。
4. 最近记录、导出和数量预览使用一致商品筛选口径。
5. 概览显示 SKU 覆盖、Top SKU 和 SKU 高频问题 Top 5。
6. 趋势显示 SKU 问题簇的两个 7 天周期变化和显著上升标记。
7. SKU 问题簇可创建按平台和 SKU 限定的处理任务。
8. SKU 任务快照、显著上升和效果复盘不混入其他 SKU。
9. 原有无 SKU 数据、普通问题簇、趋势、任务和复盘行为保持兼容。
10. Python、Node、JavaScript 语法、严格 UTF-8、差异检查和浏览器验收全部通过。
11. 不新增模型请求、海外平台 API、后台轮询、自动重试或第三方前端依赖。

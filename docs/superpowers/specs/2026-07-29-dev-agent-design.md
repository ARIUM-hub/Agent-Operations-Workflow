# 研发助手型智能体第一版设计

日期：2026-07-29

## 背景与目标

本项目从空仓库开始，目标是设计并实现一个个人使用的研发助手型智能体。第一版以代码开发助手为主，项目流程助手为辅，优先打通“需求到代码”的完整闭环，同时为问题修复、代码优化和项目流程辅助保留扩展空间。

智能体的默认形态是 Windows 优先的终端工具，支持高自动执行、多轮协作、强验证、项目级规则、增强历史记忆、本地 Web 控制台，以及云端模型 provider 插件化。第一版既要能作为独立 CLI 工具运行，也要为接入 Codex 等现有智能体环境保留适配层。

## 已确认需求

- 使用对象：个人使用。
- 核心场景：代码开发为主，项目流程辅助为次。
- 第一优先闭环：需求理解、代码修改、验证、总结、Git 交付。
- 交互形态：自然语言为主，少量基础命令为辅。
- 执行模式：高自动执行，遇到关键节点进行多轮协作。
- 技术栈支持：Python 与 Node.js/TypeScript 双优先。
- 运行平台：Windows 优先，尤其关注 PowerShell、路径和 UTF-8 编码。
- Git 能力：可提交、可推送，但灾难性操作强制拦截。
- 项目规则：仓库内规则为主，本机个人偏好叠加。
- 历史记忆：增强版任务历史，会提炼明确偏好和经验。
- 记忆检索：关键词检索与向量检索混合。
- 模型能力：云端 API 为主，provider 插件化。
- 供应商保护：需要强保护，包括预算、并发限制、冷却和熔断。
- Web 面板：本地 Web 控制台，支持任务提交、审批、日志、规则和历史。

## 推荐方案

第一版采用“CLI 核心 + 本地 Web 控制台”。

CLI 是主要工作入口，负责自然语言任务、代码修改、命令执行、Git 操作和验证。Web 控制台是辅助入口，负责查看任务历史、项目规则、执行日志，也支持提交任务和审批关键节点。Python 负责智能体编排、工具调用、模型 provider、记忆检索和执行策略；TypeScript/Node.js 负责 CLI 工程体验、本地 Web 控制台和前端交互。

相比纯 CLI，这个方案保留了可视化任务和审批体验；相比平台优先方案，它不会让第一版被复杂 UI、状态同步和权限系统拖重。

## 范围

### MVP 包含

- 自然语言 CLI 任务入口。
- 本地 Web 控制台，可提交任务、审批关键节点、查看日志、查看历史、查看规则。
- Python 智能体编排内核。
- Node.js/TypeScript CLI 与 Web 控制台。
- Python 与 Node.js/TypeScript 项目识别。
- 项目规则加载与本机偏好叠加。
- 任务历史记录与经验提炼。
- 关键词 + 向量混合检索。
- 云端模型 provider 插件接口，第一版内置一个主 provider。
- 强验证策略：测试、lint、类型检查、构建尽量跑全。
- Git status、branch、commit、push 能力。
- 模型请求预算、并发限制、重试限制、冷却与供应商熔断保护。
- Windows PowerShell 与 UTF-8 编码作为一等约束。

### MVP 不包含

- 远程多人协作平台。
- 复杂权限系统。
- IDE 插件深度集成。
- 大量模型供应商内置实现。
- 本地模型优先运行。
- 自动处理生产环境发布。
- 未经确认的大规模并发子智能体执行。

## 架构

系统分为四层：

1. 入口层：CLI 与本地 Web 控制台。
2. 核心层：Python 智能体编排内核。
3. 适配层：项目适配、模型 provider、Git、命令和测试工具。
4. 持久化层：项目规则、本机偏好、任务历史、向量索引和审计日志。

CLI 与 Web 控制台共享同一个任务引擎，不各自实现执行逻辑。Web 控制台通过本地服务与任务引擎通信，用于展示任务状态、审批请求和历史记录。Python 内核对外暴露清晰的任务接口，TypeScript 层只负责用户体验、命令包装和本地页面。

## 核心组件

### CLI

CLI 默认接受自然语言任务，例如：

```powershell
dev-agent "实现登录接口"
```

第一版只保留少量基础命令：

- `init`：初始化仓库规则。
- `doctor`：检查运行环境、模型配置、Git 状态和常用工具。
- `history`：查看历史任务。
- `serve`：启动本地 Web 控制台。

### Web 控制台

Web 控制台包含五个视图：

- 任务：查看当前计划、进度、命令和验证结果。
- 审批：处理 Git push、策略切换、高风险操作等确认。
- 日志：查看工具调用摘要、命令输出和错误分类。
- 规则：查看仓库规则和本机偏好合并结果。
- 历史：查看历史任务、经验提炼和成本摘要。

### 智能体编排内核

编排内核负责：

- 理解自然语言任务。
- 扫描仓库上下文。
- 加载项目规则和个人偏好。
- 检索相关历史经验。
- 生成执行计划。
- 调用工具读写文件、执行命令、修改代码。
- 在关键节点请求用户确认。
- 运行强验证。
- 生成交付总结。
- 写回任务历史和经验。

### 项目适配

第一版正式支持 Python 与 Node.js/TypeScript 项目。适配器需要识别常见文件，例如 `pyproject.toml`、`requirements.txt`、`package.json`、`tsconfig.json`、`pytest.ini`、`vitest.config.*` 等，并推断安装、测试、lint、类型检查和构建命令。

适配器推断出的命令低于显式项目规则优先级。若仓库内 `.agent/commands.yaml` 指定了测试命令，应优先使用该命令。

### 模型 Provider

模型 provider 使用插件化接口。第一版只内置一个主云端 provider，但接口必须支持后续扩展到 OpenAI 兼容 API、DeepSeek、Anthropic 或其他云端模型。

provider 层必须接入成本保护、并发限制、重试限制、冷却和熔断状态，不能让上层任务绕过这些限制。

## 数据流

任务从 CLI 或 Web 控制台进入后，按以下流程执行：

1. 接收自然语言任务。
2. 扫描仓库、Git 状态、依赖文件和项目规则。
3. 加载本机个人偏好。
4. 使用关键词 + 向量检索召回相关历史经验。
5. 生成任务上下文包。
6. 生成执行计划。
7. 按计划读文件、修改代码、执行命令。
8. 遇到关键节点时进入多轮协作确认。
9. 运行强验证。
10. 生成变更总结、验证结果和后续建议。
11. 按策略执行 Git commit 或 push。
12. 写回任务历史、验证命令、失败模式和有效经验。

## 安全与成本保护

第一版采用“高自动 + 轻量拦截”，但对灾难性操作和模型供应商熔断保持强保护。

常规研发命令默认自动执行，包括读文件、改代码、安装已声明依赖、运行测试、lint、类型检查和构建。影响较大的节点需要协作确认，例如大范围重构、验证失败后的策略切换、远程 Git push、项目规则变更。灾难性操作强制拦截，例如强制覆盖 Git 历史、递归删除关键目录、生产环境命令、批量模型压力请求、绕过冷却时间的高频请求。

模型调用必须限制：

- 单任务最大请求数。
- 单任务最大重试次数。
- 并发请求数。
- 最大上下文扩展次数。
- 预算上限。
- 供应商冷却时间。
- 供应商熔断状态。

当出现连续失败、限流、超预算或熔断信号时，系统停止高频请求，给出中文风险警告、预计请求量和安全替代方案，不进行批量重试或频繁切换模型。

## 记忆与配置

仓库共享规则建议放在 `.agent/` 目录：

- `.agent/project.yaml`：项目说明、技术栈、默认策略。
- `.agent/rules.md`：代码规范、协作偏好、禁用操作。
- `.agent/commands.yaml`：测试、lint、类型检查、构建和 Git 策略。

本机个人配置建议放在 `%USERPROFILE%/.dev-agent/`：

- `preferences.yaml`：语言偏好、审批偏好、默认工作习惯。
- `providers.yaml`：模型 provider 配置与密钥引用。
- `budgets.yaml`：请求预算、冷却时间和供应商保护策略。

运行时由 Context Resolver 合并仓库规则、本机偏好、实时扫描结果和历史召回。优先级从高到低为：显式用户本轮指令、灾难性操作拦截规则、仓库规则、本机偏好、自动扫描结果、历史经验。

任务历史记录结构化信息，包括任务输入、计划、关键决策、工具调用摘要、验证命令、Git 结果、最终总结和经验提炼。关键词检索负责稳定命中项目、命令、文件和错误文本；向量检索负责召回相似任务、修复经验和个人偏好。

敏感信息只保存在本机配置，不写入仓库共享规则。第一版只自动提炼明确偏好，不自动改写核心项目规则。

## 错误处理

错误分为四类：

- 命令失败：命令不存在、退出码非零、环境缺失、路径错误。
- 验证失败：测试、lint、类型检查或构建失败。
- 模型失败：超时、限流、预算不足、供应商熔断。
- 权限失败：文件访问、Git 远程、审批缺失。

低风险错误允许自动恢复，例如重读上下文、缩小改动范围、重跑相关验证、调整命令推断。若恢复路径不确定，系统必须给出 2-3 个下一步选择，并说明风险和推荐选项。最终失败也要记录到历史中，沉淀失败模式和后续建议。

## 验证策略

第一版默认强验证。项目支持时，优先运行完整测试、lint、类型检查和构建。若完整验证成本过高或项目规则指定了范围，可以先运行受影响模块验证，再补全局验证。验证命令来源优先级为项目规则、适配器推断、用户本轮指定。

交付总结必须包含实际运行过的验证命令和结果，不能在未运行验证时声称通过。

## Git 策略

系统可以查看 Git 状态、创建分支、提交和推送。默认在交付前展示 diff 摘要和验证结果。远程 push 属于协作确认节点；破坏性 Git 操作属于强制拦截。

允许自动化的 Git 操作包括读取 `status`、`diff`、`log`，以及在任务完成后按规则提交。需要确认的操作包括 push、创建远程分支、大范围重命名。强制拦截操作包括 `reset --hard`、强制 push、删除主分支、清理未跟踪文件等破坏性动作。

## 并发策略

第一版只做有限并发。默认由单主智能体串行推进。只有任务天然独立、请求量可控、不会触发供应商高频请求风险时，才允许少量子任务并行，例如分别分析前端、后端、测试或文档。

并发执行必须遵守供应商请求保护。任何批量探测模型、循环健康检查、压力测试接口、批量重试失败请求、绕过冷却时间反复切换模型的行为都需要停止并提示风险。

## Windows 与编码约束

第一版 Windows 优先。所有命令执行、路径处理和文件读写需要优先兼容 PowerShell。文本文件默认 UTF-8。遇到包含中文的代码或配置文件时，不使用 `\uXXXX` 转义，直接读写正常中文字符，并在命令层尽量设置 UTF-8 输出，避免终端编码与文件编码不一致导致乱码。

依赖安装需要考虑国内网络环境，默认建议使用国内镜像或可配置镜像源，但不能在未确认风险时批量探测多个供应商或接口。

## 设计验收标准

- 能在 Windows 上初始化项目规则。
- 能通过 CLI 接受自然语言研发任务。
- 能识别 Python 与 Node.js/TypeScript 项目基础结构。
- 能加载仓库规则、本机偏好和历史经验。
- 能生成可读执行计划并按多轮协作推进。
- 能直接修改代码并运行强验证。
- 能在 Web 控制台查看任务、日志、审批、规则和历史。
- 能执行 Git 提交与确认后推送。
- 能在模型限流、超预算或熔断风险下停止高频请求并给出中文风险提示。
- 能记录任务历史并在后续任务中召回相关经验。

## 实施顺序建议

后续实现计划应优先按以下顺序拆分：

1. 仓库骨架、配置模型和 Windows 编码基线。
2. CLI 基础入口与本地配置初始化。
3. Python 编排内核与任务状态模型。
4. 项目扫描与 Python/Node 适配器。
5. 模型 provider 接口与成本熔断保护。
6. 工具执行器、Git 能力和强验证。
7. 任务历史、关键词检索与向量检索接口。
8. 本地 Web 控制台。
9. 端到端需求到代码闭环验证。

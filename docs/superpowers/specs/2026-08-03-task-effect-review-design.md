# 任务效果复盘设计

## 背景

客户使用问题归因智能体已经具备“会话分析、人工复核、运营概览、问题趋势、创建处理任务、推进任务并记录处理结果”的本地运营流程。当前任务在填写处理结果后即进入已完成状态，但系统无法回答处理措施是否让同类客户问题减少。

本轮将任务闭环延伸到效果验证：系统按统一口径展示处理前后的同类问题数量，运营基于数据人工确认“有效、无明显变化或恶化”，并保留可修正、可审计的复盘记录。

## 已确认目标

- 只对已完成任务提供效果复盘。
- 固定比较任务创建前 7 天与任务完成后 7 天的同一问题簇记录。
- 完成满 7 天后才能提交最终复盘，未满 7 天显示数据积累状态。
- 系统提供数据证据，不自动替代运营做最终判断。
- 人工结论固定为“有效、无明显变化、恶化”，复盘说明必填。
- 允许修正已提交的复盘，底层保留每一次历史事件。
- 继续使用本地 UTF-8 JSONL 追加事件流，不增加数据库、模型调用或平台 API。

## 非目标

- 不做 14 天、30 天或自定义周期的多轮复盘。
- 不自动判定最终复盘结论。
- 不自动轮询复盘成熟时间，不发送站内或外部通知。
- 不增加用户、登录、复盘人身份或团队权限模型。
- 不增加完整历史记录浏览器，不改变最近 10 条记录区域的语义。
- 不修改分析记录、人工反馈、现有任务创建事件或 CSV 导出字段。
- 不连接 Amazon、TikTok Shop 或其他海外电商平台接口。
- 不进行模型请求、供应商探测、批量重试或压力测试。

## 推荐架构

沿用现有 `tasks.jsonl`，新增专用 `task_effect_reviewed` 事件。`TaskStore` 负责按文件顺序把最新复盘投影到任务，`TaskService` 负责复盘成熟状态、两个时间窗口、问题簇匹配、证据重算和业务校验，FastAPI 只负责请求模型、状态码和响应映射。

任务列表不为每张任务卡扫描全部分析记录。列表中的复盘成熟状态只依赖任务状态、`completed_at`、当前时间和是否已有复盘；只有运营打开复盘面板或提交复盘时，后端才读取 `analyses.jsonl` 并计算证据。

## 复盘事件模型

每次首次提交或修正都追加一个完整证据事件：

```json
{
  "type": "task_effect_reviewed",
  "task_id": "task-example",
  "reviewed_at": "2026-08-17T10:00:00+00:00",
  "review": {
    "revision": 2,
    "verdict": "effective",
    "note": "更新安装视频后，同类问题明显减少。",
    "baseline": {
      "start": "2026-07-27T08:00:00+00:00",
      "end": "2026-08-03T08:00:00+00:00",
      "record_ids": ["record-1", "record-2", "record-3"],
      "count": 3
    },
    "effect": {
      "start": "2026-08-10T10:00:00+00:00",
      "end": "2026-08-17T10:00:00+00:00",
      "record_ids": ["record-4"],
      "count": 1
    },
    "delta": -2,
    "change_rate": -0.6667
  }
}
```

字段规则：

- `revision` 从 1 开始，每次修正递增 1。
- `verdict` 只能是 `effective`、`no_clear_change`、`worsened`。
- `note` 去除首尾空白后必须非空。
- `baseline.count` 和 `effect.count` 必须分别等于对应 `record_ids` 的长度。
- `delta = effect.count - baseline.count`。
- `change_rate = delta / baseline.count`，四舍五入到 4 位小数；基准期为 0 条时固定为 `null`。
- `reviewed_at` 使用 UTC ISO 8601 时间。

`TaskStore.list_tasks()` 在任务投影中增加：

```json
{
  "effect_review": {},
  "effect_review_revision_count": 2
}
```

投影时把事件顶层的 `reviewed_at` 合并进最新 `effect_review`，供任务卡和修正表单直接显示。未复盘任务的 `effect_review` 为 `null`，修订次数为 0。任务列表只返回最新复盘，所有历史修订继续保存在 JSONL 事件流中。

## 复盘状态

每个任务返回 `effect_review_state` 和 `effect_review_ready_at`。状态枚举为：

- `not_applicable`：任务仍为待处理或处理中。
- `accumulating`：任务已完成，但当前时间早于完成时间加 7 天。
- `ready`：任务已完成且已满 7 天，尚未提交复盘。
- `reviewed`：已经至少提交一次复盘。

`effect_review_ready_at` 对已完成任务等于 `completed_at + 7 天`，未完成任务为 `null`。已有复盘时状态固定为 `reviewed`。

页面中的“待复盘”数量只统计 `ready`，不包含 `accumulating`。

## 时间窗口与记录匹配

时间统一转换为 UTC 瞬间，窗口使用左闭右开区间：

```text
基准期：[created_at - 7 天, created_at)
效果期：[completed_at, completed_at + 7 天)
```

左闭右开可保证边界确定；即使任务在创建后立即完成，同一条记录也不会同时进入两个窗口。两个窗口之间的任务处理期不参与比较。

记录必须同时满足：

- `created_at` 可以解析，且位于指定窗口。
- 记录 ID 是非空字符串。
- 平台去除首尾空白后使用不区分大小写的精确匹配。
- 问题类型精确匹配任务的 `issue_category`。
- 责任方精确匹配任务的 `responsibility`。
- 使用原始分析字段，不用人工修正字段改变历史统计口径。

记录按 `analyses.jsonl` 文件顺序保存到证据快照。0 条基准记录或 0 条效果记录都合法；系统只展示事实，不根据数量自动写入人工结论。

## API 设计

### 获取任务列表

扩展现有接口：

```text
GET /api/tasks?status=&priority=&effect_review_state=
```

`effect_review_state` 支持 `not_applicable`、`accumulating`、`ready`、`reviewed` 精确筛选，空值表示不筛选。未知值返回 `422`。

现有 `counts` 保持兼容，新增：

```json
{
  "effect_review_counts": {
    "accumulating": 1,
    "ready": 2,
    "reviewed": 4
  }
}
```

数量始终基于全部任务，只有 `tasks` 应用状态、优先级和复盘状态组合筛选。

### 获取复盘证据

```text
GET /api/tasks/{task_id}/effect-review
```

后端读取最新分析记录并返回：

```json
{
  "task_id": "task-example",
  "state": "ready",
  "ready_at": "2026-08-17T10:00:00+00:00",
  "evidence": {
    "baseline": {},
    "effect": {},
    "delta": -2,
    "change_rate": -0.6667
  },
  "latest_review": null,
  "revision_count": 0
}
```

只有已完成且满 7 天的任务可以获取完整复盘证据。未完成或仍在积累数据返回 `409`，任务不存在返回 `404`。已有复盘时仍重新计算当前证据，并同时返回最新历史复盘，供运营修正。

### 提交或修正复盘

```text
POST /api/tasks/{task_id}/effect-reviews
```

请求体只接受：

```json
{
  "verdict": "effective",
  "note": "更新说明后，同类问题减少。"
}
```

后端不能接受客户端提交的数量、记录 ID、窗口或变化率。提交时重新读取分析记录、重算证据并追加事件。首次提交和修正使用同一接口，每次响应返回最新任务、最新复盘和修订次数。

错误映射：

- 任务不存在：`404`。
- 任务未完成或完成未满 7 天：`409`。
- 非法结论、空备注、未知字段或非对象请求体：`422`。
- 任务或分析数据读取失败：`500`，只让任务区域显示局部错误。

预览后如果新增或补录了窗口内的匹配记录，提交响应以后端提交时重新计算的证据为准，前端使用响应替换旧预览。

## 页面设计

### 任务区头部

- 在待处理、处理中、已完成指标旁增加“待复盘”指标。
- 增加“复盘状态”筛选：全部、数据积累中、待复盘、已复盘。
- 增加人工“刷新任务”按钮，只触发一次列表 GET 请求。
- 不添加定时器或后台轮询。

### 任务卡状态

已完成任务根据复盘状态显示：

- `accumulating`：显示“效果数据积累中”和本机格式的可复盘时间，不显示提交按钮。
- `ready`：显示“待效果复盘”和“开始复盘”按钮。
- `reviewed`：显示最新中文结论、复盘时间、备注摘要、修订次数和“查看或修正”按钮。

待处理和处理中任务不显示效果复盘入口。

### 复盘面板

复盘面板在任务卡内展开，沿用现有局部表单交互：

- 桌面端并排展示基准期和效果期，移动端改为单列。
- 每个窗口显示本机格式的起止时间、记录数量和可展开的记录 ID 列表。
- 显示增减条数和变化比例，正负方向必须有中文文字。
- 基准期为 0 条时显示“基准期 0 条，无法计算变化比例”。
- 提供三种人工结论和必填复盘说明。
- 修正时预填最新人工结论和说明，但证据使用本次 GET 重新计算的结果。
- 提交期间禁用按钮并显示提交状态，防止同一表单重复点击。
- 提交失败保留当前输入和证据，显示局部中文错误。
- 提交成功后关闭面板并只刷新一次任务区域。

记录 ID 展开仅用于核对证据。首版不新增任意历史窗口下钻，也不把最近记录区域改造成完整记录浏览器。

## 并发与刷新策略

- 页面初始化加载任务一次。
- 复盘状态筛选变化或点击人工刷新时加载任务一次。
- 打开复盘面板时请求证据一次。
- 提交复盘成功后刷新任务一次。
- 分析、反馈、概览、趋势和普通记录筛选不自动刷新任务复盘。
- 证据 GET 使用请求序号，较旧响应不得覆盖较新的面板或任务状态。
- 每个复盘表单同一时间只允许一个 POST 请求。
- 不增加自动重试、轮询、后台队列或并发模型调用。

本轮沿用现有单进程本地追加存储假设，不新增多进程文件锁。重复人工提交会形成两个可审计修订事件，不覆盖历史。

## 错误隔离与兼容性

- `tasks.jsonl` 不存在时继续返回空任务和全零复盘数量。
- 缺失、未知、引用不存在任务或结构损坏的复盘事件产生明确 `TaskStorageError`。
- 复盘事件错误与现有任务文件错误采用相同隔离边界：任务区域失败，分析、人工复核、概览、趋势、筛选和导出继续工作。
- 现有任务 API 字段保持兼容，只增加响应字段和可选查询参数。
- 现有分析记录和任务创建、更新事件无需迁移。
- 中文结论和说明直接以 UTF-8 保存，不使用 `\uXXXX` 转义。

## 测试策略

### 存储测试

- 首次复盘投影到任务。
- 多次修正返回最新复盘和正确修订次数。
- 中文备注按 UTF-8 原样保存。
- 多任务复盘事件互不影响。
- 缺失任务 ID、未知任务、缺失复盘对象和非法事件类型产生明确错误。

### 服务测试

- 未完成任务和完成未满 7 天被拒绝。
- 满 7 天边界可以复盘。
- 基准期和效果期使用正确左闭右开边界。
- 平台大小写变体合并，其他平台不混入。
- 问题类型和责任方保持精确匹配。
- 缺失、非法和窗口外时间被排除。
- 基准期 0 条时变化率为 `null`。
- 效果期 0 条可以提交任一合法人工结论。
- 非法结论、空备注和未知字段被拒绝。
- 预览后新增记录时，提交重新计算证据。
- 首次提交与修正生成递增修订号和新证据快照。
- 复盘状态、成熟时间、数量和组合筛选正确。

### API 与模板测试

- 列表返回复盘状态、成熟时间和复盘数量。
- 复盘状态过滤与现有状态、优先级组合工作。
- 证据和提交接口返回规定结构与 `404/409/422`。
- 客户端提交证据字段被拒绝为未知字段。
- 首页包含待复盘指标、复盘筛选和人工刷新入口。

### 前端行为测试

- 未完成、数据积累中、待复盘和已复盘任务显示正确内容与操作。
- 基准期、效果期、增减方向和变化比例正确渲染。
- 基准期为 0 时显示专用说明。
- 记录 ID 可以展开核对。
- 修正表单预填最新结论和备注。
- 空备注不提交，合法复盘提交一次并刷新任务一次。
- 提交失败保留输入和证据。
- 较旧证据响应不覆盖新面板状态。
- 人工刷新只发送一次任务请求，不产生轮询。
- 桌面与移动端布局可读且无横向溢出。

## 验收标准

1. 已完成任务在满 7 天前显示数据积累状态，满 7 天后进入待复盘队列。
2. 系统按固定的创建前 7 天和完成后 7 天窗口计算同一问题簇证据。
3. 证据包含窗口、记录 ID、数量、增减值和安全处理的变化率。
4. 运营必须选择有效、无明显变化或恶化，并填写非空复盘说明。
5. 后端在提交时重新计算证据，不信任客户端数量或记录 ID。
6. 复盘可以修正，每次修正追加事件并保留历史，页面显示最新结论和修订次数。
7. 任务区提供待复盘数量、复盘状态筛选和人工刷新，不增加自动轮询。
8. 任务复盘失败不影响分析、人工复核、概览、趋势、筛选和导出。
9. 不新增数据库、平台 API、外部通知、后台队列或模型调用。
10. pytest、Node 行为测试、JavaScript 语法、UTF-8、桌面/移动端复查和差异检查全部通过。

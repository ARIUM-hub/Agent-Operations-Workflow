# 问题趋势对比与异常提示设计

## 背景

客户使用问题归因智能体已经形成“导入会话、确定性归因、批量复核、筛选导出、运营概览、高频问题下钻”的本地闭环。运营当前可以知道问题集中在哪些平台、类型和责任方，但只能看到所选范围内的静态总量，无法直接判断某类问题是在上升、下降还是保持稳定。

本轮目标是在不接入平台 API、不调用模型供应商、不增加后台轮询的前提下，对比最近 7 天和前 7 天的问题簇变化，并突出达到明确阈值的明显上升项，让运营优先检查近期恶化的问题。

## 目标

1. 对比最近 7 天与前 7 天的有效分析记录数量。
2. 按“平台 + 问题类型 + 责任方”统计两个周期的问题簇。
3. 展示变化最大的 Top 5 问题簇及本期、上期、增减数量。
4. 当前周期至少 3 条且比上一周期增加至少 2 条时标记“明显上升”。
5. 点击趋势问题簇后下钻到最近记录筛选，并将概览和筛选导出范围切换到最近 7 天。
6. 单条或批量分析成功后立即刷新运营概览和趋势区。
7. 趋势失败独立降级，不影响分析、复核、筛选或导出。

## 非目标

- 不做自定义日期范围。
- 不做 30 天、月度、同比或环比切换。
- 不引入折线图、柱状图库或第三方前端依赖。
- 不做后台定时计算、自动轮询、消息推送或外部通知。
- 不接入 Amazon、TikTok Shop 或其他平台 API。
- 不增加 SKU、ASIN、店铺或产品字段。
- 不修改原始分析记录、反馈事件或现有 CSV 字段。
- 不使用人工修正后的问题类型和责任方重写原始趋势口径。
- 不调用模型，不增加供应商、代理通道或本地转发请求。

## 方案比较

### 采用：独立趋势接口

新增 `GET /api/records/trends?period=7d`。后端独立计算两个相邻周期，前端在运营概览下方渲染固定趋势区。

优点：

- 固定 7 天趋势不与现有概览的 `all`、`7d`、`30d` 选择耦合。
- 统计模块职责清晰，便于独立测试周期边界和异常阈值。
- 趋势加载失败可以独立降级。
- 后续增加其他周期时可以扩展 `period`，不改变现有 summary 响应。

代价是页面初始加载多一次本地 GET 请求。该请求只读取本地 JSONL 并做确定性聚合，不触发模型或外部服务，成本可控。

### 不采用：扩展现有 summary 接口

把趋势对象加入 `/api/records/summary` 可以减少一次请求，但会把固定 7 天比较与用户当前选择的概览范围混在同一个响应中。切换概览范围时也会重复计算不变的趋势，接口语义和刷新链路更难维护。

### 不采用：前端读取全部记录后计算

前端计算需要新增暴露全部 JSONL 记录的接口，增加传输量和数据暴露范围，并在 JavaScript 中复制日期解析与聚合规则，不符合现有后端汇总模式。

## 架构

新增独立模块：

```text
src/customer_issue_agent/trends.py
```

该模块只接收已合并反馈的 `list[dict]` 记录和可注入的当前时间，返回可直接 JSON 序列化的趋势结果。FastAPI 路由负责读取 `AnalysisStore.list_records()` 并调用趋势模块，不在 `app.py` 中实现聚合细节。

前端新增独立趋势容器和加载函数。趋势渲染复用现有中文枚举标签、问题簇字段校验、最近记录筛选和滚动行为，不增加第二套筛选状态。

## 时间口径

唯一支持的首版周期为 `7d`。以请求处理时的 UTC 当前时间 `now` 为基准：

- 当前周期：`now - 7 days <= created_at <= now`。
- 上一周期：`now - 14 days <= created_at < now - 7 days`。
- 两个周期在边界上不重叠。
- 晚于 `now` 的未来记录不进入任一周期。
- 缺失、空白或无法解析的 `created_at` 不进入任一周期。
- 无时区的 ISO 时间按 UTC 解释；带时区时间统一转换为 UTC 后比较。
- `period` 缺失或不是 `7d` 时安全回退到 `7d`。

趋势模块提供内部 `now` 参数供单元测试注入固定时间，API 不向客户端暴露该参数。

## 问题簇口径

问题簇键由以下原始分析字段组成：

1. `analysis.request.platform`
2. `analysis.attribution.issue_category`
3. `analysis.attribution.primary_responsibility`

字段缺失、空白或类型异常时统一规范为 `unknown`，与现有运营概览口径保持一致。

两个周期的问题簇取并集。因此以下情况都能显示：

- 上期为 0、本期新增的问题簇。
- 两期都有记录且数量变化的问题簇。
- 上期存在、本期降为 0 的问题簇。

本期与上期数量都为 0 的项不会产生。`delta` 定义为 `current_count - previous_count`。`delta == 0` 的稳定问题簇不进入变化列表。

人工反馈不会重写原始问题类型或责任方，因此反馈保存不会改变趋势问题簇。修正字段继续保留在反馈事件和 CSV 导出中。

## 异常阈值

首版采用固定、可解释的数量阈值：

```text
significant_increase = current_count >= 3 and delta >= 2
```

示例：

- `0 → 1`：普通上升，不提示异常。
- `1 → 2`：普通上升，不提示异常。
- `1 → 3`：明显上升。
- `3 → 5`：明显上升。
- `5 → 4`：下降，不提示异常。

不计算或展示百分比。上一周期为 0 时百分比没有稳定含义，数量差更适合当前小样本本地工作台。

## 排序与 Top 5

后端返回所有 `delta != 0` 的变化问题簇，使用确定性排序：

1. `abs(delta)` 降序。
2. `current_count` 降序。
3. `platform` 字母序升序。
4. `issue_category` 字母序升序。
5. `responsibility` 字母序升序。

前端只展示排序后的前 5 项。这样“Top 5”始终代表数量变化最大的五个问题簇，测试也可以稳定断言顺序。

## API 设计

新增：

```text
GET /api/records/trends?period=7d
```

响应示例：

```json
{
  "period": "7d",
  "current_period": {
    "start": "2026-07-24T08:00:00+00:00",
    "end": "2026-07-31T08:00:00+00:00",
    "total_records": 8
  },
  "previous_period": {
    "start": "2026-07-17T08:00:00+00:00",
    "end": "2026-07-24T08:00:00+00:00",
    "total_records": 4
  },
  "total_delta": 4,
  "clusters": [
    {
      "platform": "Amazon",
      "issue_category": "function_use",
      "responsibility": "customer_service_training",
      "current_count": 3,
      "previous_count": 1,
      "delta": 2,
      "significant_increase": true
    }
  ]
}
```

`start` 和 `end` 使用带 UTC 偏移的 ISO 8601 字符串。没有有效记录时两个总数和 `total_delta` 为 0，`clusters` 为空数组。

## 前端展示

在现有运营概览下方增加独立区域：

```text
近 7 天趋势
```

顶部展示三个轻量指标：

- 近 7 天记录。
- 前 7 天记录。
- 净变化。

下方展示 Top 5 变化问题簇。每行包含：

- 平台。
- 中文问题类型。
- 中文责任方。
- 本期数量。
- 上期数量。
- 带正负号的变化数量。
- 满足阈值时显示“明显上升”标签。

变化为正时显示 `+N`，为负时显示 `-N`。不只依赖颜色表达方向，保证可访问性。无变化问题簇时显示“最近两个周期暂无明显变化”。

不引入图表库。继续使用现有卡片、列表和 CSS 变量，使趋势区域与工作台视觉系统一致，并保证移动端换行可读。

## 点击下钻

有效趋势行渲染为按钮。点击后：

1. 校验问题类型和责任方在现有筛选下拉中存在。
2. 将概览时间范围设置为 `7d`。
3. 填入平台、问题类型和责任方。
4. 保留已有关键词和复核状态。
5. 刷新最近记录本地筛选、筛选导出条件和预计导出数量。
6. 重新加载最近 7 天运营概览。
7. 滚动到最近记录区域。

最近记录仍只筛选页面当前展示的最近 10 条；筛选导出和预计数量继续基于全部本地 JSONL，并因为时间范围切到 `7d` 而与趋势本期口径一致。

`unknown` 平台、无效问题类型或无效责任方只读展示，不渲染为下钻按钮。

## 刷新策略

- 页面 `DOMContentLoaded`：加载运营概览并加载趋势，各一次。
- 概览范围变化：只重新加载运营概览，不重新加载固定趋势。
- 单条分析成功：插入最近记录后，重新加载运营概览和趋势各一次。
- 批量分析成功：全部记录插入最近记录后，重新加载运营概览和趋势各一次，而不是每条记录刷新一次。
- 反馈保存成功：继续刷新运营概览，不刷新趋势。
- 筛选条件变化：只刷新本地列表、导出提示和预计数量，不刷新趋势。

不增加定时器、自动轮询、失败重试循环或后台任务。

## 数据流

1. 页面调用 `/api/records/trends?period=7d`。
2. 路由从 `AnalysisStore` 读取已合并反馈的记录。
3. `trends.py` 解析时间并分配到两个互斥周期。
4. 模块计算总量、问题簇并集、差值、异常标记和稳定排序。
5. 前端渲染三个指标和 Top 5 变化问题簇。
6. 用户点击有效趋势行时复用现有筛选与导出链路下钻。

## 错误与边界处理

- JSONL 文件不存在或为空：返回全 0 和空列表。
- 记录结构缺失：日期无效则跳过；问题簇字段无效则归为 `unknown`。
- API 请求失败：趋势区显示“趋势加载失败，请刷新页面重试”，其他功能保持可用。
- API 返回空变化列表：显示稳定空态，不显示错误。
- 页面缺少趋势容器：加载函数直接返回，不发请求。
- 页面缺少筛选控件：趋势保持只读，不抛错。
- 点击无效问题簇：不改变现有筛选或时间范围。
- 新分析后的趋势刷新失败：分析仍保持成功，最近记录已插入，不回滚记录。
- 记录恰好位于 7 天边界：只进入当前周期。
- 记录恰好位于 14 天边界：进入上一周期。
- 未来时间记录：不进入趋势，避免本机时钟异常扩大当前周期。

## 测试策略

### 趋势模块单元测试

- 当前与上一周期边界互斥。
- 7 天和 14 天边界归属正确。
- 未来、缺失和非法日期被排除。
- 无时区日期按 UTC 解释。
- 当前和上一周期总量及 `total_delta` 正确。
- 问题簇使用两个周期并集。
- 本期新增和本期归零的问题簇都能返回。
- `delta == 0` 的问题簇不返回。
- 缺失问题簇字段归为 `unknown`。
- 明显上升阈值覆盖阈值内外示例。
- 排序按绝对变化、当前数量和稳定键执行。
- 空记录返回全 0。

### API 与模板契约测试

- `/api/records/trends?period=7d` 返回完整响应。
- 未知 `period` 回退到 `7d`。
- 首页包含趋势容器、加载提示和可访问区域标签。
- 静态 JavaScript 包含趋势加载、渲染、绑定和下钻函数。
- 静态 CSS 包含趋势指标、变化方向和异常标签样式。

### 前端行为测试

使用 Node 内置 `node:test`、`assert`、`vm` 和轻量 DOM stub 加载真实 `app.js`，覆盖：

- 正负变化文案格式。
- 明显上升标签只出现在阈值项。
- 只渲染 Top 5。
- 空列表渲染稳定空态。
- 有效趋势行点击后设置三个筛选和 `7d` 时间范围。
- 下钻保留关键词和复核状态。
- 无效趋势行不绑定下钻。
- 页面加载调用趋势一次。
- 单条分析成功后趋势与概览各刷新一次。
- 批量分析成功后趋势与概览各刷新一次，而不是按记录数量刷新。
- 反馈保存不刷新趋势。
- 趋势请求失败只更新趋势错误区域。

## 验收标准

1. 页面可以看到最近 7 天与前 7 天的总量对比。
2. 页面展示变化最大的 Top 5 问题簇。
3. 当前周期至少 3 条且增加至少 2 条的问题簇显示“明显上升”。
4. 少量 `0 → 1` 或 `1 → 2` 变化不误报异常。
5. 点击有效趋势行后，平台、问题类型、责任方和最近 7 天范围正确下钻。
6. 下钻保留关键词和复核状态，并同步筛选导出条件与预计数量。
7. 单条和批量分析成功后，趋势和运营概览无需刷新页面即可更新。
8. 反馈保存、概览范围变化和普通筛选不会产生多余趋势请求。
9. 趋势加载失败不影响其他工作台功能。
10. 不新增数据库、第三方前端依赖、后台轮询或模型调用。
11. pytest、Node 行为测试、JavaScript 语法和差异检查全部通过。

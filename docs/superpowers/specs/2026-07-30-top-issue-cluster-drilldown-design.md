# 高频问题一键下钻设计

## 背景

客户使用问题归因智能体已经支持海外电商客服会话分析、人工复核、最近记录组合筛选、筛选导出、运营概览，以及按平台、问题类型和责任方组合展示 Top 5 高频问题簇。

当前“高频问题”卡片只能帮助运营识别问题集中方向。用户看到某个平台上的高频问题后，仍需要手动在“最近记录”区域依次填写平台、问题类型和责任方，才能查看对应样本。本轮目标是把问题簇从只读统计变成轻量下钻入口，在不增加模型调用和后端复杂度的前提下缩短从洞察到处理的路径。

## 目标

1. 有效的高频问题簇整行可以点击和键盘操作。
2. 点击后自动设置最近记录的以下三个筛选条件：
   - 平台。
   - 问题类型。
   - 责任方。
3. 保留用户已有的关键词和复核状态筛选。
4. 复用现有统一刷新链路，同步更新当前记录列表、导出条件提示、预计导出数量和待复核快捷按钮。
5. 点击后滚动到“最近记录”区域，方便立即查看当前页面中的匹配样本。
6. 支持任意可表示的平台名称，不把能力限定为 Amazon 或 TikTok Shop。

## 非目标

- 不新增记录查询 API。
- 不加载全部匹配记录，仍只筛选首页当前展示的最近 10 条。
- 不改变运营概览或筛选导出的时间范围语义。
- 不改变高频问题的聚类、排序或 Top 5 统计规则。
- 不新增问题簇选中状态、再次点击取消或独立返回按钮；退出下钻继续使用现有“清空”按钮。
- 不清空关键词或复核状态。
- 不修改 JSONL 存储格式。
- 不新增模型调用、后台任务或自动重试。

## 采用方案

采用“问题簇按钮 + 专用绑定函数”。`summaryIssueClusters(items)` 把可下钻的问题簇渲染为原生 `button`，按钮通过专用 `data-*` 属性携带平台、问题类型和责任方。运营概览每次异步渲染完成后，调用独立绑定函数注册点击行为。

这个方案与现有平台分布下钻保持一致：概览负责提供筛选入口，最近记录筛选控件继续作为唯一筛选状态来源，`refreshRecordFilterViews()` 继续负责刷新所有相关视图。

不采用以下方案：

- 概览父容器事件委托。实现代码较少，但会与现有“重绘后绑定”模式形成两套事件管理方式。
- URL 查询参数下钻。它支持刷新恢复和分享链接，但需要扩展首页参数解析，超出本轮轻量目标。
- 新增后端记录查询接口。它可以展示全部匹配记录，但会扩大 API、分页和动态记录渲染范围，本轮先保持最近 10 条语义。

## 前端结构

### 问题簇渲染

`summaryIssueClusters(items = [])` 保留现有卡片和列表结构。每个可下钻的问题簇渲染为包含以下属性的按钮：

- `data-summary-issue-cluster-filter`：绑定钩子。
- `data-summary-cluster-platform`：原始平台值。
- `data-summary-cluster-issue-category`：问题类型枚举值。
- `data-summary-cluster-responsibility`：责任方枚举值。

所有动态属性和可见文本都继续经过 `escapeHtml()`。按钮的 `aria-label` 包含平台、中文问题类型、中文责任方和记录数量，确保读屏用户能够理解点击结果。

空摘要继续显示“暂无数据”和数量 `0`，不渲染按钮。

### 可下钻判断

平台筛选是文本输入，可以表示任意非空平台名称。问题类型和责任方是固定下拉框，因此只有满足以下条件的问题簇才可点击：

1. 平台不是空值或 `unknown`。
2. `issue-filter` 存在与问题类型值匹配的选项。
3. `responsibility-filter` 存在与责任方值匹配的选项。

不满足条件的历史异常问题簇仍展示统计，但使用静态行，不提供点击行为。这样可以避免用户点击后只有部分筛选条件生效。

### 事件绑定

新增 `bindSummaryIssueClusterFilters(root = document)`。它查找所有带 `data-summary-issue-cluster-filter` 的按钮，使用现有 `data-bound` 约定避免重复绑定，并在点击时读取三个专用数据属性。

`renderRecordsSummary(summary)` 完成 `innerHTML` 重绘后，依次绑定现有平台下钻和问题簇下钻。每次时间范围切换都会重新渲染概览，因此新按钮会获得新的事件绑定。

### 应用组合筛选

新增 `applySummaryIssueClusterFilter({ platform, issueCategory, responsibility })`。函数执行以下步骤：

1. 获取 `platform-filter`、`issue-filter` 和 `responsibility-filter`。
2. 再次验证三个值都可由对应控件表示；任一控件缺失或值无效时直接返回，不进行部分更新。
3. 写入三个筛选控件。
4. 不修改 `record-search` 和 `feedback-filter`。
5. 调用 `refreshRecordFilterViews()`。
6. 平滑滚动到“最近记录”区域。

为了避免平台下钻和问题簇下钻重复维护滚动逻辑，可以抽取小型 `scrollToRecentRecords()` helper，并让现有 `applySummaryPlatformFilter()` 复用它。该重构不改变平台下钻行为。

重复点击同一个问题簇会再次写入相同值并刷新，不切换或清空筛选。用户需要退出时使用现有“清空”按钮。

## 数据流

1. 页面根据当前运营概览时间范围请求 `/api/records/summary`。
2. 后端按现有逻辑返回 `top_issue_clusters`。
3. 前端渲染高频问题卡片，并把有效问题簇渲染为按钮。
4. 用户点击问题簇。
5. 前端设置平台、问题类型和责任方筛选，保留关键词与复核状态。
6. `refreshRecordFilterViews()` 筛选当前最近 10 条、刷新导出条件提示、请求真实导出数量并同步待复核按钮。
7. 页面滚动到最近记录区域。

本功能不新增接口或请求类型。点击后仍会由现有 `updateExportCountPreview()` 发起导出数量刷新，它继续使用全部 JSONL 记录和当前时间范围计算真实匹配数量。

## 时间范围与展示口径

运营概览的 `全部记录`、`最近 7 天` 和 `最近 30 天` 继续决定高频问题统计范围。点击问题簇不会改变当前时间范围。

“最近记录”仍只包含首页初始加载的最新 10 条，也不会新增时间范围过滤。因此当前 10 条可能没有匹配样本，此时显示现有“没有符合条件的记录”提示。筛选导出条件和预计导出数量仍包含当前运营概览时间范围，并反映全部 JSONL 中的真实匹配结果。

## 视觉与可访问性

- 问题簇按钮保持现有卡片的文字层级和数量布局，不引入新的视觉系统。
- 按钮覆盖整行可点击区域，并移除浏览器默认边框和背景，使其与分布列表一致。
- `hover` 使用轻量背景或文字颜色变化表达可点击性。
- `focus-visible` 提供清晰轮廓，不能只依赖颜色提示。
- 静态异常行不显示指针光标或交互状态。
- 桌面端继续占两列，`900px` 以下继续回落为单列。

## 错误与边界处理

- `top_issue_clusters` 为空或缺失：显示现有空状态，不绑定按钮。
- 平台为空或为 `unknown`：该问题簇只读展示。
- 问题类型或责任方无法在下拉框中表示：该问题簇只读展示。
- 点击时筛选控件缺失或值已失效：不修改任何筛选条件。
- 当前最近 10 条无匹配：复用现有列表空状态。
- 导出数量请求失败：继续显示现有“预计数量暂不可用”。
- HTML 特殊字符平台名：动态属性、文本和 `aria-label` 都进行转义。

## 文件改动

- Modify: `src/customer_issue_agent/static/app.js`
  - 渲染问题簇按钮。
  - 新增可下钻判断、事件绑定、组合筛选和共享滚动 helper。
- Modify: `src/customer_issue_agent/static/styles.css`
  - 增加问题簇按钮默认、悬停和键盘焦点样式。
- Modify: `tests/test_app.py`
  - 覆盖按钮数据属性、绑定函数、筛选控件、统一刷新和滚动钩子。
  - 覆盖问题簇按钮样式钩子。
- Modify: `README.md`
  - 说明问题簇下钻范围、保留条件及导出数量语义。

后端摘要、API、模板、领域枚举、存储和模型逻辑均不修改。

## 测试策略

1. 先更新静态 JavaScript hook 测试，要求脚本包含：
   - `data-summary-issue-cluster-filter`。
   - 三个问题簇数据属性。
   - `bindSummaryIssueClusterFilters`。
   - `applySummaryIssueClusterFilter`。
   - 三个筛选控件 ID。
   - `refreshRecordFilterViews` 和滚动 helper。
2. 运行聚焦测试，确认实现前因缺少新钩子而失败。
3. 实现最小 JavaScript 行为并确认聚焦测试通过。
4. 先更新 CSS hook 测试，再实现按钮的默认、悬停和 `focus-visible` 样式。
5. 运行完整 `pytest` 测试套件。
6. 运行 `node --check src/customer_issue_agent/static/app.js`。
7. 运行 Git 差异和工作树检查。
8. 手动验收：
   - 点击有效问题簇后，三个筛选值正确写入。
   - 关键词和复核状态保持不变。
   - 当前列表、导出条件和预计数量同步更新。
   - 无当前样本时显示空状态。
   - 键盘可以聚焦并激活按钮。
   - 移动端布局保持单列。

## 验收标准

1. 运营可以从高频问题卡片一键设置平台、问题类型和责任方筛选。
2. 下钻只影响当前最近 10 条的页面展示，完整匹配数继续由现有预计导出数量提供。
3. 关键词、复核状态和运营概览时间范围不会被清空。
4. 重复点击不取消筛选，现有“清空”按钮可以退出下钻。
5. 无法完整表示的异常问题簇不可点击。
6. 所有动态内容安全转义，按钮支持键盘和清晰焦点状态。
7. 不新增后端 API、存储字段或模型调用。
8. 完整测试、JavaScript 语法检查和差异检查通过。
